# Releasing CatKeyper

CatKeyper releases are published automatically by GitHub Actions when a maintainer pushes a semantic version tag.

The release workflow:

- validates the tag name
- extracts the version from the tag
- runs tests
- builds ZIP and DMG artifacts with `make release VERSION=<version>`
- extracts matching release notes from `CHANGELOG.md`
- creates a GitHub Release
- uploads the ZIP and DMG assets

## Prerequisites

- Push access to `https://github.com/DooD73/catkeyper`
- A clean `main` branch containing the changelog entry for the version being released
- A tag in the format `vX.Y.Z`, for example `v1.1.0`
- [`create-dmg`](https://github.com/create-dmg/create-dmg) 1.3.0 or newer for local DMG builds (`brew install create-dmg`)

No personal access token is required. The release workflow uses the built-in `GITHUB_TOKEN` with `contents: write`.
The workflow installs `create-dmg` on its macOS runner before packaging.

## Branded DMG contract

`make dmg VERSION=<version>` packages the signed `build/CatKeyper.app` with
`create-dmg`. Keep these values stable unless the background artwork and this
checklist are updated together:

- volume name: `CatKeyper`
- Finder window: 660 × 400 points at screen position 200, 120
- icon size: 116 points
- `CatKeyper.app`: 175, 235
- Applications shortcut: 485, 235
- background: `assets/dmg-background.png` (660 × 400)
- editable background source: `assets/dmg-background.svg`
- volume icon: `assets/AppIcon.icns`

The checked-in PNG makes release builds independent of SVG conversion tools.
When the SVG changes, export it at exactly 660 × 400 pixels, update the PNG in
the same commit, and open a locally built DMG to check the final Finder layout.
`create-dmg` stores the layout in hidden `.DS_Store` metadata and keeps the
background in a hidden `.background` directory inside the image.

Packaging uses the checked-in `assets/AppIcon.icns` so every release receives
the reviewed icon bytes. Run `make icon` only when intentionally regenerating
that asset from `assets/openmoji-cat-face.svg`, and review the resulting ICNS
before committing it.

## 1. Prepare the changelog

Move release-ready items from `Unreleased` into a versioned section. The parser expects a second-level heading for the version:

```markdown
## [1.1.0] - 2026-07-01

### Added

- New release item
```

The parser also accepts `## [v1.1.0] - 2026-07-01`, but the unprefixed SemVer form is preferred.

If the matching section is missing or empty, the workflow publishes fallback notes of `Release vX.Y.Z` and emits a warning.

## 2. Commit the release notes

```bash
git switch main
git pull --ff-only
git add CHANGELOG.md
git commit -m "update changelog for v1.1.0"
git push origin main
```

Skip the commit if the changelog entry is already on `main`.

## 3. Create and push the release tag

Use an annotated tag:

```bash
git tag -a v1.1.0 -m "v1.1.0"
git push origin v1.1.0
```

Pushing the tag starts `.github/workflows/release.yml`.

## 4. Monitor the workflow

Open the repository Actions tab and watch the `Release` workflow for the tag.

The workflow should produce:

- `build/catkeyper-<version>-macos.zip`
- `build/catkeyper-<version>-macos.dmg`
- `build/catkeyper-macos.zip`
- `build/catkeyper-macos.dmg`

When the job succeeds, GitHub Releases will contain a published release named after the tag, with versioned artifacts and stable latest-download aliases attached.

## 5. Verify the published release

Download the latest assets from:

- `https://github.com/DooD73/catkeyper/releases/latest/download/catkeyper-macos.zip`
- `https://github.com/DooD73/catkeyper/releases/latest/download/catkeyper-macos.dmg`

If using the versioned asset filenames generated by the workflow, download them from the release page for the tag.

Before testing first launch, verify the downloaded artifact itself:

1. Run `hdiutil verify catkeyper-macos.dmg`.
2. Mount the DMG and confirm Finder opens a 660 × 400 branded window named
   `CatKeyper`.
3. Confirm only `CatKeyper.app` and the Applications shortcut are presented,
   at the documented positions, with the arrow pointing from the app to
   Applications. Hidden `.DS_Store` and `.background` metadata are expected.
4. Drag `CatKeyper.app` onto Applications and confirm the copy completes.
5. Verify the copied app without changing its signature:
   `codesign --verify --deep --strict --verbose=2 /Applications/CatKeyper.app`.

Then, on a clean supported macOS account or VM with no existing CatKeyper
Accessibility entry:

1. Confirm copying the app did not add or enable Accessibility permission.
2. Open `CatKeyper.app` from Applications. Because current releases are
   ad-hoc signed and not notarized, follow the current Gatekeeper recovery path
   if needed: right-click the app, choose **Open**, then confirm.
3. Confirm macOS requests Accessibility access only after first launch. If it
   does not, add and enable CatKeyper in **System Settings > Privacy & Security
   > Accessibility**, then restart the app.
4. Lock keyboard input from the menu bar.
5. Unlock with the menu bar button.
6. Lock again and unlock with the Shift+CAT chord.
7. Eject the DMG and remove the test copy and Accessibility entry before
   repeating clean-account QA for another build.

## Dry-run testing

The workflow contains a `DRY_RUN` environment variable. Temporarily set it to `"true"` in `.github/workflows/release.yml` on a test branch if you need to validate version parsing, changelog extraction, tests, and artifact generation without creating a GitHub Release.

Return `DRY_RUN` to `"false"` before merging.

## Troubleshooting

- `create-dmg: command not found`: install it with `brew install create-dmg`, then rerun `make dmg VERSION=<version>`.
- `Release tags must match vX.Y.Z`: create a tag like `v1.1.0`; prerelease and build metadata tags are not accepted by the current workflow.
- `Expected release asset ... was not created or is empty`: inspect the `make release` output. The workflow expects the Makefile to create both ZIP and DMG files using the parsed version.
- `GitHub Release ... already exists`: delete the existing release or create a new SemVer tag.
- Missing changelog notes: add a `## [X.Y.Z] - YYYY-MM-DD` section to `CHANGELOG.md` and tag again with a new version.
